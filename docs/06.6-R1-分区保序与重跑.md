# 步骤 6.6 记录：修复补数据乱序，重跑 R1 MVP

- 日期：2026-11-03
- 前置：[06.5 首次运行](06.5-R1-MVP首次运行.md)：故障恢复后补数据，流量窗口丢了 76%
- 结果：干净重跑后，三项对账全部对平

## 结论

问题有两层，都已修复，并且都在虚拟机上验证过：
1. **DWD 补数据时打乱分区顺序。** 修法是让 ODS 和 DWD 的分区一一对应（同一用户落在同一分区号），补数据时 DWD 各分区仍然有序。
2. **下游读事务 topic 时空闲超时太短**，被误判成空闲的分区会让 Watermark 跳进。修法是空闲超时调到大于上游提交间隔。

| 对账（干净重跑） | 修复前（06.5） | 修复后 |
|---|---|---|
| 对账 A：SQL 流量窗口丢失的 pv | 338,563 条（75.66%） | **74 条（0.02%）** |
| 对账 B：DataStream 三方对账 | `unexplained = 0` | `unexplained = 0` |
| GMV：Flink vs MySQL | 10,333 单、921,384.16 元，一致 | 一致 |

## 一、为什么没用 Watermark 对齐

原计划是在 DWD 的 ODS 源上做分区级 Watermark 对齐，后来放弃了：
- 对齐的粒度是「一次拉取」：Kafka 一次拉 500 条，暂停分区要等这一批处理完。
- 这份数据在时间上很稀疏：9 天 50 万条，每个分区平均 4–5 秒事件时间才有一条，500 条就跨了 30–40 分钟事件时间。
- 所以对齐只能把乱序压到几十分钟，而下游只容忍 5 秒。

最后改用**分区一一对应**：不管各分区读得多快，每个输出分区只装一个输入分区的数据、顺序不变。从根上保证有序，不依赖读取速度。

## 二、改了什么

| 文件 | 改动 |
|---|---|
| `replayer/replayer.py` | 加 `partitioner: murmur2_random`。librdkafka 默认用 CRC32 算分区，和 Java 客户端（Flink）的 murmur2 不一致 |
| `sql/10_dwd_user_behavior.sql` | sink 加 `user_key`（user_id 的字符串）作消息 key：`key.format = raw`，`value.fields-include = EXCEPT_KEY`（value 内容不变）。显式写出异步 Lookup 按输入顺序输出（`ORDERED`） |

| `bin/check_order.sh`（新增） | 量化每个分区「落后超过 5 秒」的比例，核对 ODS 和 DWD 的分区是否一一对应；可用 `DWD_TOPIC=` 指定要检查的 topic |
| `bin/reset.sh` | 清理时也删掉实验用的 `dwd_catchup` |

## 三、验证过程（都在虚拟机上跑）

### 1. 回放中途停掉 HBase 3 分钟（10:46–10:49）
- DWD 作业 **0 次异常**：维表查询开了本地缓存，用户 7,798 个、商品 29,769 个，前 8 分钟就全部缓存住了，停机期间根本不用访问 HBase。
- 面试可讲：Lookup 缓存不只能提升性能，还能在维表存储短时故障时兜底。代价是维表更新后，最多要等 1 小时缓存过期才能生效。
- 这次没造出积压，所以补数据场景另外单独验证，见第 2 项。

### 2. 补数据实验：新 DWD 作业一次性读完 50 万条积压，写到 `dwd_catchup`
- 18 秒全部写完，用 `check_order.sh` 检查：

| 分区 | ODS 乱序比例 | `dwd_catchup` 乱序比例 | 修复前 DWD（06.5） |
|---|---|---|---|
| 0 | 1.42% | 1.42% | 61.2%，最多落后 92 小时 |
| 1 | 1.42% | 1.42% | 67.4% |
| 2 | 1.51% | 1.51% | 64.5% |

- 3 个分区的用户都一一对应，没有错位的用户。剩下约 1.4% 的乱序就是回放器故意注入的迟到数据，最多落后 3 分钟，和设计一致。

### 3. 第一次修复后的实时运行：对账 A 仍丢 6.8%
- DWD 已经有序，但流量窗口还是丢了 30,432 条，比注入的迟到 pv（6,652 条）多 2.4 万条。
- **根因**：
  - DWD 是事务写入，下游 `read_committed` 每 30 秒才看到一批数据，相当于 5 小时事件时间。
  - 空闲超时是 10 秒，批与批之间各分区都被判成空闲。
  - 新一批到达时，先被读到的分区独自推进全局 Watermark，其他分区的数据随后到达就成了迟到数据。
- **修复**：空闲超时改成 90 秒。用新配置的流量作业从头重算，差额降到 16 条。

### 4. 干净重跑（11:10–11:36，不注入故障）
- 对账 A 只差 74 条，对账 B `unexplained = 0`，GMV 一致。
- **注入的迟到数据大多没被 SQL 窗口丢掉，原因有两点：**
  - 事务批次大：每批约 5 小时事件时间；
  - Watermark 是周期性生成的，默认 200 毫秒一次。

  同一批里的迟到数据在 Watermark 越过窗口前就已经处理完了，所以迟到判定要看到达时的 Watermark，不是看注入了多少秒。DataStream 作业直接读非事务的 ODS，仍然有 2,702 条迟到 180 秒的数据进了侧输出。

## 面试可以怎么讲

> 「故障恢复后补数据，我们的实时 UV/PV 掉了 76%。我量化了每个分区的乱序：ODS 分区有序，DWD 分区却落后最多 92 小时。原因是 DWD 单并行度读 3 个分区，追数时各分区速度不一，输出又被重新分区。Watermark 对齐的粒度是一次拉取，对稀疏数据不够，所以我让上下游使用同一个分区算法（librdkafka 默认 CRC32，Java 是 murmur2），保证 ODS 分区 p 只进 DWD 分区 p。修完又发现下游读事务 topic 时空闲超时小于上游的提交间隔，会让 Watermark 跳进。两处修完后实时窗口和离线重算只差 0.02%。」
