# 步骤 6.7 记录：Doris Routine Load 卡住的根因

- 日期：2026-11-03 至 11-04
- 现象：实验第一轮回放时，ODS 导入一格一格地跳，分区 0 长时间显示 `OFFSET_ZERO`；两个读已提交的导入（窗口结果、迟到数据）26 分钟里一行都没导
- 结果：查出 3 个叠在一起的原因，全部修复，并在实时回放下验证通过

## 结论

| # | 原因 | 影响 | 修复 |
|---|---|---|---|
| 1 | **Doris 4 的自适应批次**：Routine Load 有积压时，每批强制至少 360 秒（`routine_load_adaptive_min_batch_interval_sec = 360`），一批跑完才提交 | 实时回放期间数据一直在写，任务永远读不到末尾，每 6 分钟才可见一次 | FE 配置降到 10 秒（`04-doris.sh` 写进 fe.conf） |
| 2 | **事件时间被写成了 Kafka 消息时间戳**：Flink DataStream 的 Kafka sink 默认用元素的时间戳，也就是 2017 年 | Kafka 的日志滚动和 48 小时保留都按消息时间戳算，几分钟内整段日志被当成过期删掉。**Kafka 里的数据丢了**，Doris 从 offset 0 读会越界 | topic 设 `message.timestamp.type=LogAppendTime`（`env.sh` 的 `create_topic`） |
| 3 | **Doris BE 复用坏掉的 Kafka 消费者**：消费者按「broker + topic + 属性」匹配后放进连接池复用。一个消费者因为第 2 点卡住后，每一轮都被拿出来用 | 那个导入一直 0 行；同一个坏消费者被复用了一整天 | Routine Load 的 `group.id` 每次运行带不同后缀，每轮都新建消费者 |

验证（实时回放 6 分钟，三项修复全上）：ODS 只落后约 1 分钟；窗口结果和迟到数据每次 Flink 提交后很快导入，回放停下时 Lag 都是 0。修复前，同样条件下这两个导入是 0 行。

## 排查过程（每一步都有证据）

1. **先排除「读已提交」本身。** 第二轮极速回放时，两个读已提交的导入正常，ODS 却卡了 6 分钟，说明问题和隔离级别无关。
2. **推测「topic 删除重建后复用旧消费者」，被否定。** 查 Doris 源码 `KafkaDataConsumer::match()`，确认它只比较 broker、topic 名和属性。但对照实验里，删除重建同名 topic 后，属性相同的任务也只用 6 秒就导完了。
3. **从 BE 日志找到 360 秒（原因 1）。** 每个任务都打印 `max time(ms): 360000`，第二轮 ODS 正好在 6 分钟后追平。查 FE 源码 `KafkaTaskInfo.adaptiveBatchParam` 和配置项，找到 `routine_load_adaptive_min_batch_interval_sec = 360`。
4. **对照实验：读已提交本身没问题。** 用 librdkafka 事务生产者每 10 秒提交一次，读已提交的导入每次都很快跟上；读未提交的反而要等生产者停了才导入，这又一次印证了原因 1。
5. **在第一轮的条件下复现。** 把配置降到 10 秒后，ODS 正常了，但窗口结果还是 0 行。看 Kafka 日志，起始 offset 被推进到 427；server.log 显示刚建 40 秒就滚动了日志段，又按保留策略删掉。只有 Java 作业写的两个 topic 受影响，由此找到原因 2。
6. **修完原因 2，迟到数据还是 0 行。** Python librdkafka 和 Java 消费者都能读到全部 776 条，14 个事务全部提交。BE 日志里，这个导入用的消费者 ID 和前一天卡住的那个完全一样，由此找到原因 3。换 group.id 后 12 秒就导完了 776 条。

## 改了哪些文件

| 文件 | 改动 |
|---|---|
| `setup/04-doris.sh` | fe.conf 加 `routine_load_adaptive_min_batch_interval_sec = 10`（虚拟机上已同步写入，同时在运行时生效） |
| `mvp/bin/env.sh` | `create_topic` 加 `message.timestamp.type=LogAppendTime`；topic 被自动重建时也会再设置一次 |
| `mvp/sql/doris_routine_load.sql` | 3 个 `group.id` 都加 `-@LABEL_SUFFIX@` |

## 顺带理清的几件事

- `check.sh` 里 Doris 的行数比 Routine Load 统计的少，是因为任务还没提交，统计里包含了正在进行的事务，这是正常的。
- 前几天的运行最后都追平了，是因为碰巧导入任务在 Kafka 删数据之前就把数据读走了。原因 2 一直存在，只是没有暴露出来。
- 第一轮 ODS 分区 0 一直是 `OFFSET_ZERO`，是因为 3 个分区由 3 个消费者在同一个 6 分钟的批次里抢着读，读得快慢不一。降到 10 秒后，每批都会推进所有分区。

## 面试可以怎么讲

> 「Doris 的实时表一会儿 6 分钟不更新，一会儿完全不进数。我没有直接调参数，而是先分层定位：Kafka 侧用 Java 和 librdkafka 两种客户端验证数据完整，再看 Doris BE 日志里每个导入任务的时长、行数和消费者 ID。结果发现三个叠在一起的问题：
> 一是 Doris 4 的自适应批次在有积压时每批至少 360 秒；
> 二是 Flink 把 2017 年的事件时间写成了 Kafka 消息时间戳，Kafka 按时间戳做保留，几分钟就把数据删了；
> 三是 Doris 会复用 Kafka 消费者，一个被删数据搞坏的消费者被反复复用了一整天。
> 第二个最危险，因为它会在 Kafka 层面直接丢数据。所以我把消息时间戳统一改成写入时间，事件时间只放在消息内容里。」
